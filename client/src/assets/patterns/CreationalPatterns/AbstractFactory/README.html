Intent

Provide an interface for creating families of related objects without specifying their concrete classes.

Instead of constructing products directly, you ask a kit to produce them. Every kit produces a compatible family: terrain that matches its enemies, enemies that drop biome-appropriate loot, weather that belongs to that world. Swap the kit and the entire world changes. The client that builds the world never knows or cares which kit it's holding.

Why "Kit" Not "Factory"

The GoF book's Known Uses section names this explicitly. ET++ used WidgetKit as its abstract factory, with MotifWidgetKit and PMWidgetKit as the concrete implementations. The suffix Kit signals that you're producing a coordinated set of things that belong together, not just a single object.

The concrete factory name always contains the abstract name: DesertBiomeKit tells you it is a BiomeKit, specifically the desert one. You never have to look up what kind of kit it is. The naming is self-documenting.

The Problem It Solves

A procedural world generator needs to spawn terrain, enemies, weather, and loot. Each must be internally consistent. You cannot have arctic enemies dropping desert spice or forest weather playing over frozen tundra. Without a pattern, you'd scatter if (biome === 'desert') checks across every system that creates something.

With Abstract Factory, that check happens once: when you choose a kit. After that, WorldGenerator just calls kit.createTerrain(), kit.createEnemies(), and so on. It has no idea whether it's building a desert, arctic, or forest world. It doesn't need to.

Patterns at Work

This implementation deliberately layers three patterns:

  • Abstract Factory. BiomeKit defines the product family contract. Swap the kit, swap the world.
  • Singleton. Each concrete kit has exactly one instance. The enemy registry is shared state; multiple calls to a kit return clones from the same prototype pool.
  • Prototype. createEnemies() doesn't construct enemies from scratch. It streams the registry and calls Enemy::clone() on each. New enemy types can be pushed into the registry at runtime via registerEnemy() without touching any factory class.

Stable vs. Changing Interface

This is the central tension of Abstract Factory. The BiomeKit interface is the stable contract. Every client, every test, every caller depends on it. Once it exists, changing it is expensive.

Adding a new family (a fourth biome, SwampBiomeKit) is free. You write one new class that implements the existing interface. Nothing else changes. This is the pattern working as intended.

Adding a new product type (a fifth method, createAmbientSound()) breaks the stable interface. Every concrete kit must be updated, and any client that depends on the interface must recompile. The pattern does not protect you here. This is the known cost, and it is why you design the interface carefully upfront.

The rule: families grow easily, product slots do not. Choose this pattern when the product types are settled and the variants are what will grow.

Consequences

The GoF names four specific consequences. All four show up here.

✓ Concrete Isolation

WorldGenerator never imports SandWorm, IceTerrain, or SpiceLoot. It only knows BiomeKit, Terrain, Enemy, WeatherSystem, and LootTable. Adding a fourth biome requires zero changes to the client.

✓ Exchanging Product Families

The entire world is determined by which kit you pass in. The demo runs all three kits through the same WorldGenerator loop: identical client code, three completely different worlds. In a real game, this is a single variable at startup.

✓ Consistency Across Products

DesertBiomeKit returns a sandstorm, scorpions, sand dunes, and spice loot. Everything belongs together. The pattern enforces this at the architectural level. It is impossible to get arctic weather paired with desert enemies because the same kit produces both, and kits do not cross-pollinate.

That is of course if we don't create a DesertArticHybridBiomeKite DesertArticHybridBiomeKite with sandstorms and penguins.

✗ Difficulty of New Products

Adding a fifth product type means adding a method to BiomeKit and implementing it in all three concrete kits. There is no shortcut. The Prototype trick only softens this within the Enemy slot: new enemy types register at runtime, but a new product category still touches every factory.

When to Reach For It

  • You have multiple families of objects that must be used together and never mixed
  • The choice of family is made once and then used everywhere
  • You want client code that is completely agnostic to which concrete family it's working with
  • The number of families will grow, but the set of product types will stay stable

Trade-offs

Strengths
  • Products from one factory are guaranteed compatible
  • Swap an entire system by changing one reference
  • Client code has zero dependency on concrete classes
  • Adding a new family only adds a new kit class
Weaknesses
  • Adding a new product type touches every existing factory
  • More classes and interfaces than simpler alternatives
  • Overkill if you only have one product family that never changes
