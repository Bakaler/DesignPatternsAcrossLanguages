Composite

Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly — the same interface works whether you're talking to a leaf or to the whole tree.

Intent

You have a tree of objects. Code that works on a single node should work identically on a subtree or the entire tree, without the caller ever having to check which it's talking to. The Composite pattern enforces this by making every node — leaf and container alike — implement the same Component interface.

Participants

  • Component — the shared interface. Declares operations that make sense for both leaves and composites (e.g. getCapacity(), addConnection(), getOutgoingRoutes()).
  • Leaf — a node with no children. Implements Component directly. In this demo: Airport. Each airport manages its own connections and 24-hour departure schedule.
  • Composite — a node that holds children and implements Component by delegating to them. In this demo: AirportNetwork. Adding a connection, removing one, or querying total capacity all recurse through every child airport.
  • Client — talks only to the Component interface. Never cares whether it has a single airport or the whole US network.

Structure

The interface that ties everything together: 

interface AirNetworkComponent {
  getName(): string;
  getCapacity(): number;           // leaf: its own cap  |  composite: sum of all children
  addConnection(route): void;      // leaf: push locally  |  composite: delegate to children
  removeConnection(id): void;
  getOutgoingRoutes(): Route[];
}

Airport (Leaf) implements each operation directly on its own data: 

class Airport implements AirNetworkComponent {
  getCapacity() { return this.capacity; }

  addConnection(route) {
    if (!this.connections.find(r => r.id === route.id))
      this.connections.push(route);
  }

  getOutgoingRoutes() {
    return this.connections.filter(r => r.from === this);
  }
}

AirportNetwork (Composite) implements the same interface by iterating its children — the recursion is invisible to callers: 

class AirportNetwork implements AirNetworkComponent {
  private airports: Airport[] = [];

  // Aggregates across all children — caller sees one number
  getCapacity() {
    return this.airports.reduce((sum, a) => sum + a.getCapacity(), 0);
  }

  // Propagates the connection down to both endpoint leaves
  addConnection(route) {
    this.routes.push(route);
    route.from.addConnection(route);
    route.to.addConnection(route);
  }

  // Cascades the removal to every child that holds a reference
  removeConnection(routeId) {
    this.routes = this.routes.filter(r => r.id !== routeId);
    this.airports.forEach(a => a.removeConnection(routeId));
  }
}

The key insight

The scheduling engine that dispatches flights at a given hour doesn't know it's calling into a composite — it just calls network.getDeparturesAtHour(hour). That single call fans out across every airport in the tree, collects their scheduled departures, and returns one flat list. The client wrote zero looping code.

This uniformity is the payoff: adding a new airport to the network doesn't change any calling code, and querying the full network is syntactically identical to querying a single airport.

When to use

  • Your domain has a natural part-whole hierarchy (file systems, UI components, org charts, transport networks).
  • You want client code to ignore the difference between individual items and collections of items.
  • Operations on a group should be the same as operations on a single member.

Trade-offs

  • Pro: Open/Closed — adding new leaf types doesn't change composites or clients.
  • Pro: Recursive operations (total capacity, full schedule) come for free.
  • Con: The common interface can become too general if leaves and composites have meaningfully different operations (e.g. "add child" doesn't make sense on a leaf).
  • Con: Type safety requires careful design — restricting child-management operations to composites only means either casting or a richer interface hierarchy.

Related patterns

  • Decorator — also uses recursive composition, but wraps a single object rather than managing a collection of children.
  • Flyweight — often used inside Composite leaf nodes to share intrinsic state across many instances.
  • Iterator — natural companion for traversing composite trees.
