Intent

Compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly. The same interface works at every level of the tree.

You have a tree of objects. Code that operates on a single node should work identically on a subtree or the whole tree, without the caller ever checking which it is talking to. The Composite pattern enforces this by giving every node the same Component interface, whether it is a leaf or a container.

The Problem It Solves

An airline network needs to track total capacity and outgoing routes. The network contains airports. Airports belong to regional groupings. Code that queries the whole network, a single region, or a single airport should not need to know which level it is at.

Without Composite, every query becomes a type check. Is this a network, a region, or an airport? Is it a leaf or a container? Add a new level to the hierarchy and every caller needs to be updated.

With Composite, every node answers the same questions. Call getCapacity() on the top-level network and the call recurses through every region and every airport automatically. The caller writes zero looping or branching code.

Structure

The interface that ties the entire tree together: 

interface AirNetworkComponent {
  getName(): string;
  getCapacity(): number;        // leaf: own cap  |  composite: sum of children
  addConnection(route): void;   // leaf: push locally  |  composite: delegate down
  removeConnection(id): void;
  getOutgoingRoutes(): Route[];
}

The Three-Level Tree

This demo uses a three-level hierarchy rather than the textbook two. This is where the pattern earns its keep. 

AirportNetwork          ← top-level Composite
  └── RegionalNetwork   ← mid-level Composite
        └── Airport     ← Leaf

Calling network.getCapacity() at the top triggers one reduce across regions, each of which triggers its own reduce across airports. Three levels, one method call, zero special cases.

Participants

Role In This Implementation Responsibility
Component (interface) AirNetworkComponent Declares the shared operations (getCapacity(), getOutgoingRoutes(), addConnection()) that every node must implement regardless of depth.
Leaf Airport Terminal node. Implements Component directly on its own data. Manages its own capacity, carrier list, and 24-hour departure schedule.
Composite (mid-level) RegionalNetwork Holds a collection of Airports. Implements Component by delegating to children. getCapacity() sums its airports, getOutgoingRoutes() flattens them.
Composite (top-level) AirportNetwork Holds a collection of RegionalNetworks. Same interface, one level higher. The root of the tree and the entry point for all queries.
Client Scheduling engine, itinerary planner, stats bar Talks only to AirNetworkComponent. Never checks what level it is at. Calls getCapacity() and gets back the right number whether it asked the root or a leaf.

Consequences

The GoF names three specific consequences. All three are visible in this demo.

✓ Defines Class Hierarchies of Primitive and Composite Objects

Airport, RegionalNetwork, and AirportNetwork are distinct classes with different internal structures, but from the outside they are identical. The stats bar that displays total network capacity does not know it is iterating three levels of tree. It just calls getCapacity().

✓ Makes the Client Simple

The scheduling engine that dispatches flights at a given hour calls network.getDeparturesAtHour(hour) once. That single call fans out across every region and every airport, collects scheduled departures, and returns one flat list. The client wrote zero looping code and has no knowledge of the tree structure beneath it.

✓ Makes It Easy to Add New Kinds of Components

Adding a new level, say a continent-level grouping above regions, requires one new class that implements AirNetworkComponent. No existing code changes. The stats bar, the itinerary planner, and the scheduling engine all continue to work without modification.

✗ Can Make Design Overly General

The shared interface forces every node to answer the same questions. Operations that only make sense on a composite, like adding a child, end up on the shared interface, which means leaf nodes must either implement them as no-ops or throw. This is the classic tension in Composite: a cleaner interface versus type-safe child management.

When to Reach For It

  • Your domain has a natural part-whole hierarchy such as file systems, UI component trees, org charts, transport networks, or bill-of-materials
  • You want client code to be blind to the difference between individual items and collections of items
  • Operations on a group should be syntactically identical to operations on a single member
  • You expect the hierarchy depth to change over time and do not want that change to ripple into every caller

Trade-offs

Strengths
  • Open/Closed. Add a new node type without changing composites or clients
  • Recursive operations come for free. Capacity, routes, and departures all cascade automatically
  • Client code stays clean regardless of tree depth
  • Adding tree levels is a single new class
Weaknesses
  • The shared interface can become too general if leaves and composites have meaningfully different operations
  • Type safety requires careful design. Child management methods on the interface mean leaves must handle calls that do not apply to them
  • Tightly couples the entire tree to a single interface. Changing that interface touches every node

Related Patterns

Decorator Iterator Flyweight Visitor

Decorator. Also uses recursive composition but wraps a single object rather than managing a collection of children. Where Composite aggregates, Decorator augments.
Iterator. Natural companion for traversing composite trees without exposing internal structure. Lets you walk the whole tree with a single iterator.
Flyweight. Often used inside Composite leaf nodes to share intrinsic state across many instances. Useful when a tree has thousands of identical leaves.
Visitor. Lets you add operations to a Composite tree without modifying node classes. Visitor and Composite are frequently used together.
