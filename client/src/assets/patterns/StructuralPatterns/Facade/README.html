Intent

Provide a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.

You have subsystems. Each subsystem has its own interface, its own auth, its own quirks. Clients that need to coordinate them must know all of that detail and spread it everywhere. Facade puts one class in front of all of it. Clients talk to the facade. The subsystems never know a facade exists.

The Problem It Solves

A purchase flow needs to validate a token, charge a card, and send a confirmation message. That means talking to three separate third-party APIs, each with its own base URL, its own auth header format, and its own request/response shape.

Without Facade, every consumer that needs to do anything involving these systems must know all of that. Change one auth header and you are hunting down every caller. Add a new third party and the blast radius is the entire codebase.

With Facade, that knowledge lives in exactly one place per subsystem. PurchaseService calls auth.validateToken(token), payment.charge(userId, amount), and messaging.send(phone, message). It has no idea what headers those calls carry, what base URLs they target, or what the raw response shapes look like.

Participants

Role In This Implementation Responsibility
Abstract Facade Base ThirdPartyClient Owns the HTTP plumbing oncerequest, get, post, header masking, mock response. Subclasses inherit it for free.
Facade A PaymentFacade Wraps PaymentProcessorTP. Defines its base URL, auth headers, and exposes charge(), refund(), getTransaction().
Facade B AuthFacade Wraps AuthProviderTP. Defines its bearer format, client ID header, and exposes validateToken(), getUser().
Facade C MessagingFacade Wraps MessagingTP. Defines its account SID + auth token headers and exposes send(), getStatus().
Consumer PurchaseService Calls facade methods only. References zero raw TP details no base URLs, no header names, no endpoint paths.

Consequences

The GoF names three specific consequences. All three show up here.

✓ Shields Clients from Subsystem Components

PurchaseService references no TP class, no base URL, no auth header. It calls three methods and gets results. If PaymentProcessorTP changes its auth mechanism tomorrow, only PaymentFacade needs updating. Zero cascading changes to callers.

✓ Promotes Weak Coupling

Subsystems can be swapped entirely. Replace PaymentProcessorTP with a different processorrewrite PaymentFacade and nothing upstream notices. The facade is the only coupling point between the TP and the rest of the codebase.

✓ Doesn't Prevent Direct Access

The GoF lists this as a benefit, not a warning. Subsystems remain directly accessible for callers that need the full API. The facade is a convenience layer, not a gate. Advanced consumers can bypass it without breaking the pattern. The risk is that they will, and then you are back to scattered TP knowledge everywhere.

✗ God-Object Risk

Every new TP endpoint is a candidate to land on the facade. Left unchecked, PaymentFacade ends up with thirty methods and becomes harder to maintain than the raw TP it was hiding. The pattern does not protect you here. Discipline does.

The Base Class Decision

The GoF describes Facade as a single class wrapping a subsystem. This implementation goes one step further: an abstract base class (ThirdPartyClient) owns the HTTP plumbing so each concrete facade only defines its configuration and methods.

The trade-off is intentional. Without the base class, every facade duplicates the same fetch logic, the same header formatting, the same error handling. The base class eliminates that repetition and means improvements to the HTTP layer (retry logic, logging, timeout handling) happen once and apply everywhere.

It also means each concrete facade is a very short class. The config is three lines. The methods are one-liners. That is the intent of the pattern working correctly.

When to Reach For It

  • You have a complex or poorly designed subsystem that callers should not need to understand
  • There are many dependencies between clients and the implementation classes of an abstraction
  • You want to layer your subsystemseach layer gets a facade that is the entry point to that layer
  • Third-party APIs: every one of them is a candidate for a facade

Trade-offs

Strengths
  • Callers are shielded from subsystem complexity
  • Swap a subsystem by updating one class
  • Single place for error handling, logging, retry logic
  • Subsystems remain directly accessible when needed
Weaknesses
  • Can become a god-object if every feature gets bolted on
  • Adds a layer of indirection that may not always be worth it
  • Developers can bypass the facade and re-scatter TP knowledge

Related Patterns

Abstract Factory Mediator Singleton

Abstract Factory. Can be used with Facade to provide an interface for creating subsystem objects in a subsystem-independent way.
Mediator. Both abstract functionality of existing classes. Mediator centralises communication between peer objects that know about each other. Facade defines a simpler interface to a subsystem whose objects do not know the facade exists. Key difference: bidirectional vs. one-directional.
Singleton. Facades are often Singletons because only one facade object is needed per subsystem.
