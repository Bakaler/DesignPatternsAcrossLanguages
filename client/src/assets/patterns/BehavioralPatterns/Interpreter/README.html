Intent

Given a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language.

Each grammar rule becomes a class. Sentences in the language are represented as abstract syntax trees (ASTs) composed of those classes. To evaluate a sentence, you call interpret() on the root, which recurses through the tree with each node handling its own rule.

The Problem It Solves

Some problems recur often enough to benefit from a small, specialised language (a DSL). The alternatives are either:

  • A monolithic if/else/switch that handles every case in one place, making it hard to extend
  • An ad-hoc string-processing approach that is fragile and untestable

The Interpreter pattern formalises the grammar as a class hierarchy. Each class is self-contained, testable in isolation, and adding a new grammar rule means adding a new class. No existing class changes.

Where This Came From: the EBNF_parser

This implementation grew out of a real calculator's EBNF_parser, a recursive-descent parser with one method per grammar rule (_exp, _term, _factor, _digit). That is the Interpreter pattern expressed as methods rather than classes.

The GoF version externalises each rule into its own class so trees become first-class objects you can store, pass, reuse, and evaluate against multiple contexts. The single-class method approach does not support this.

Participants

Role In This Implementation Responsibility
AbstractExpression Expression (interface) Declares interpret(ctx). Every node in the tree must implement it.
TerminalExpression NumberExpression Leaf node. Returns a literal number. Does not recurse.
TerminalExpression VariableExpression Leaf node. Looks up its name in the Context. Does not recurse.
NonterminalExpression AddExpression, SubtractExpression, MultiplyExpression, DivideExpression Composite nodes. Each holds two child Expressions and combines their results.
Context Context Holds variable-to-value bindings. Passed to every interpret() call.
Client Entry point Builds expression trees from the participant classes and calls interpret().

The Key Insight: Tree Reuse

A tree built once can be evaluated against any number of contexts. This is what separates the GoF Interpreter from a simple recursive evaluator: the expression is an object, not a string or a one-shot computation. 

  // Build once
  tree = (a + b) * (a - b)

  // Evaluate many times with different contexts
  tree.interpret({a: 10, b: 5})  → 75   (= 10² - 5²)
  tree.interpret({a:  6, b: 2})  → 32   (=  6² - 2²)
  tree.interpret({a:  3, b: 1})  →  8   (=  3² - 1²)

This is analogous to compiling a function and calling it with different arguments. The structure (compiled code / AST) is immutable; the inputs vary.

Consequences

✓ Grammar as Classes

Each grammar rule is a self-contained class. This makes the grammar explicit and navigable: find the rule, find the class. The hierarchy mirrors the grammar.

✓ Easy to Extend

Adding a new operation (say, ModuloExpression) requires one new class implementing interpret(). No existing class changes. This is open/closed in the most literal sense.

✓ Context Reuse

The same expression tree can be evaluated repeatedly with different Contexts. The tree is immutable; only the variable bindings change. A query language, a rules engine, or a formula evaluator all benefit from this separation.

✗ Class Explosion

For complex grammars, the class count grows rapidly: one class per rule, per operator, per keyword. A language with 30 operators becomes 30 classes. For large grammars, parser generators (ANTLR, yacc) are more practical.

✗ Tightly Coupled to Grammar

Changing the grammar (removing a rule, merging two rules) requires restructuring the class hierarchy. If the grammar is in flux, the cost of keeping the class structure in sync may outweigh the pattern's benefits.

When to Reach For It

  • The grammar is simple and stable: a handful of rules, unlikely to change radically
  • You need to evaluate the same expression many times with different inputs
  • Tree traversal performance is acceptable (it is slower than a native eval)
  • You want the grammar to be readable in the code, not hidden in a parser table

Classic examples: regular expression engines, SQL WHERE clause evaluators, configuration DSLs, rules engines, and template languages.

Trade-offs

Strengths
  • Grammar is explicit in the class hierarchy
  • New operations require only a new class
  • Trees are objects: storable, passable, reusable
  • Each node is independently testable
Weaknesses
  • One class per grammar rule; explodes for large grammars
  • Grammar changes restructure the class hierarchy
  • Tree traversal is slower than compiled evaluation
  • No built-in parsing; you still need to build the tree

Related Patterns

Composite Visitor Iterator

Composite. The expression tree is a Composite. NonterminalExpressions are composite nodes (they hold children); TerminalExpressions are leaves. Interpreter applies Composite to the specific problem of grammar evaluation.
Visitor. If you need multiple independent operations over the same tree (evaluate, pretty-print, optimise), Visitor separates those operations from the node classes. Interpreter keeps the operation inside each node; Visitor externalises it.
Iterator. Can be used to traverse the nodes of the AST without exposing its structure.
