Intent

Define the skeleton of an algorithm in a base class, deferring some steps to subclasses. Subclasses can redefine certain steps without changing the algorithm's structure.

The base class owns the sequence. Subclasses own the variation. The template method says: here are the steps and their fixed order. Fill in the ones that differ per context. Everything that is invariant (shared validation, shared output) is written once and inherited by all.

The Hollywood Principle

"Don't call us, we'll call you."

In Template Method, the base class calls the subclass, never the other way around. DataPipeline.run() calls _extract(), which is implemented by CsvPipeline. The subclass never calls run() itself. It just provides its piece; the base orchestrates.

This inversion of control is the defining characteristic of the pattern and the source of its code reuse. The expensive shared logic (_validate(), _load()) lives in the base and runs automatically for every subclass without any cooperation required from the subclass author.

Abstract Steps vs. Hook Methods

Not all steps are the same kind of override point. The GoF distinguishes two types:

Type In This Implementation Behaviour
Abstract step _extract() · _transform() No default. Subclass must implement. Raises TypeError if not.
Concrete step _validate() · _load() Full implementation in base. Subclasses should not override.
Hook _report() Default implementation provided (prints errors or "no issues"). Subclasses may override for custom post-run messaging.

Hooks are the escape valve. They give subclasses a sanctioned extension point without forcing them to implement something. A subclass that doesn't need custom reporting ignores _report() entirely and gets the default for free.

Participants

Role In This Implementation Responsibility
Abstract Class DataPipeline Defines run(), the template method. Implements shared steps. Declares abstract steps.
Concrete Class CsvPipeline Parses CSV rows. Trims whitespace, normalises empty values to None.
Concrete Class JsonPipeline Parses a JSON array. Flattens nested dicts, coerces numeric strings.
Concrete Class XmlPipeline Walks XML elements. Strips type attributes, coerces values to int / float / bool / str.

Consequences

✓ Code Reuse

_validate() and _load() are written exactly once in DataPipeline. All three concrete pipelines get them for free. Add a fourth format and you get validation and load output without writing a line.

✓ Enforced Sequence

run() is the template. It is not virtual. No subclass can call the steps in a different order, skip validation, or run load before extract. The invariant sequence is a guarantee, not a convention.

✓ Hollywood Principle

The base class drives. Subclasses are passive: they provide implementations and wait to be called. A new pipeline author only needs to think about parsing and cleaning. The orchestration is not their problem.

✗ Inheritance Lock

The algorithm lives in the class hierarchy. Adding a new step (say, _audit() after _load()) requires editing DataPipeline and potentially adding abstract or hook methods that all existing subclasses must satisfy. Deep inheritance also becomes hard to read when subclasses override multiple steps - following the execution path requires jumping between files.

Template Method vs. Strategy

These two patterns solve the same problem (varying part of an algorithm) but in opposite ways.

Template MethodStrategy
Mechanism Inheritance Composition
Variation Subclass overrides steps Inject a different object
Algorithm owner Base class Context class
Runtime switch No (fixed at class definition) Yes (swap the strategy object)

Prefer Strategy when you need to switch algorithms at runtime or compose behaviours. Prefer Template Method when the algorithm structure is fixed and subclassing is natural.

When to Reach For It

  • Multiple classes share the same algorithm structure but differ in specific steps
  • You want to enforce a sequence of operations that subclasses cannot bypass
  • You want shared "before" and "after" logic (validation, logging, teardown) without repeating it
  • The variation is best expressed as a class, not a callable

Trade-offs

Strengths
  • Shared steps written once; DRY by design
  • Algorithm sequence is a hard guarantee
  • Adding a new variant is a single new class
  • Hollywood principle keeps subclasses simple
Weaknesses
  • Inheritance couples subclass to base class
  • New required steps require touching every subclass
  • Can't swap algorithm variants at runtime
  • Deep hierarchies become hard to trace

Related Patterns

Strategy Factory Method Hook Method

Strategy. Achieves the same variation goal via composition instead of inheritance. Prefer Strategy when runtime switching is needed.
Factory Method. Is often a special case of Template Method: the template method calls a factory method as one of its steps, letting subclasses decide what to instantiate.
Hook Method. Not a GoF pattern on its own, but a technique used within Template Method. A hook is a concrete method with a default no-op or default behaviour that subclasses may override.
