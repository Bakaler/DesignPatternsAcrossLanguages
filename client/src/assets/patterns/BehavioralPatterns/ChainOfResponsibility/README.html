Intent

Avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Chain the receiving objects and pass the request along the chain until an object handles it.

Each handler in the chain decides: do I handle this, or do I pass it on? A request that reaches the end of the chain without being claimed is rejected. The sender knows nothing about which handler will respond.

The Problem It Solves

When you have a token, event, or request that could be handled by one of several objects, but the sender should not know which one, you need a way to route it without a monolithic if/else chain.

  • A giant switch statement that handles every token type in one place is fragile and hard to extend
  • Direct coupling between sender and receiver prevents reordering, inserting, or swapping handlers

CoR puts each handler in its own class. The chain is assembled at runtime. Adding a new handler means adding a new class and inserting it into the chain. No existing code changes.

Where This Came From: the EBNF_parser

The EBNF_parser in the Scientific Calculator validates button presses against a grammar one token at a time. Its methods form a natural chain: 

  _exp()      handles  + -
    ↓ pass
  _term()     handles  * / // %
    ↓ pass
  _factor()   handles  ( )
    ↓ pass
  _power()    handles  **
    ↓ pass
  _function() handles  abs  sqrt  neg  …
    ↓ pass
  _digit()    handles  0-9  .
    ↓ None    ← rejected, no handler claimed the token

Each method either returns a result (claims the token) or calls the next method (passes it on). This is Chain of Responsibility expressed as method calls rather than handler objects. The GoF version externalises each link into its own class so the chain becomes explicit, configurable, and testable in isolation.

Participants

Role In This Implementation Responsibility
Handler Handler (abstract) Defines handle(token, ctx) and set_next(). Provides _pass() to forward to the next link.
ConcreteHandler SolveHandler, ExpHandler, TermHandler, PowerHandler, FactorHandler, FunctionHandler, DigitHandler Each claims exactly its own tokens and calls _pass() for everything else.
Context ParseContext Carries trailing, paren_depth, and has_decimal: the state handlers need to validate positional rules.
Client build_chain() Assembles the chain and returns its head. The caller only ever holds the head.
Pipeline TreeBuilder, parse_and_build() Consumes CoR results to build an Interpreter expression tree (shunting-yard). The only code that knows about both patterns.

The Full Pipeline

CoR and Interpreter connect through TreeBuilder. Neither pattern knows about the other. Only TreeBuilder imports from both. 

  tokens
    │
    ▼  build_chain()
  CoR handlers          validate & classify each token
  (Solve/Exp/Term/…)    returns (type, processed) or None
    │
    ▼  TreeBuilder
  shunting-yard         consumes results, builds the tree
                        respects precedence and grouping
    │
    ▼  .interpret(ctx)
  Expression tree       each node evaluates itself recursively
    │
    ▼
  result
  tree = parse_and_build(["2", "+", "3", "*", "4", "="])
  tree.interpret(Context())   →  14     ← 2 + (3*4), precedence respected

  tree = parse_and_build(["(", "2", "+", "3", ")", "*", "4", "="])
  tree.interpret(Context())   →  20     ← (2+3)*4, parens override

  parse_and_build(["+", "5"])
  → ValueError: Invalid token '+' after None  ← CoR rejected it first

Consequences

✓ Decoupled Validation

Each handler knows only its own tokens. ExpHandler has no idea that DigitHandler exists. You can reorder, remove, or replace handlers without touching any other class.

✓ Ordered Chain = Grammar Precedence

The chain position of each handler encodes its precedence in the grammar. Reading build_chain() top-to-bottom tells you the entire grammar hierarchy at a glance.

✓ Easy to Extend

Adding a new operator or function means adding one class and inserting it at the right position in the chain. No existing handler changes. The test in TestChainExtension demonstrates this with cbrt.

✓ Explicit Rejection

None is a first-class result. Invalid input is detectable and testable at every link. You can pin exactly which handler rejected a given token and why.

✗ No Guarantee of Handling

If no handler claims a token, it silently returns None. The caller must check for this explicitly or wrap in parse_and_build() which raises a ValueError.

When to Reach For It

  • More than one object may handle a request, and the handler isn't known at compile time
  • You want to issue a request to one of several objects without specifying the receiver explicitly
  • The set of handlers should be configurable or extensible at runtime
  • You are modelling a grammar, middleware stack, event pipeline, or approval workflow

Trade-offs

Strengths
  • Sender and receiver are fully decoupled
  • Chain order is explicit and readable
  • Handlers are independently testable
  • New handlers slot in without modifying existing ones
Weaknesses
  • No guaranteed handler; requests can fall through silently
  • Debugging requires tracing the full chain
  • Long chains can obscure which handler is responsible

Related Patterns

Interpreter Composite Command

Interpreter. CoR handles the parsing and validation half of the grammar pipeline; Interpreter handles the evaluation half. TreeBuilder bridges them.
Composite. Handler chains are often built from Composite structures when handlers can themselves contain sub-chains.
Command. Commands are often passed along a CoR chain. The chain decides which handler executes the command.
